# Contributing to dienr

Thanks for helping. This file covers working from a checkout: setting up,
testing, the R parity workflow, and how changes to behaviour are decided and
recorded. To *use* `dienr`, install it from PyPI instead
([getting started](docs/getting-started.md#install)).

## Setting up

`dienr` uses [uv](https://docs.astral.sh/uv/). The repository pins Python 3.13
in `.python-version` and tells uv to use its own managed interpreters
(`python-preference = "only-managed"` in `pyproject.toml`), so an active conda
environment or an old system Python doesn't leak in.

```bash
git clone https://github.com/adamyhe/dienr
cd dienr
uv sync --group dev          # .venv with dienr (editable) plus test and lint tools
uv run dienr --help
```

Add `--extra compat` on x86 machines without AVX2 (see
[install](docs/getting-started.md#install)). Supported: Python 3.11–3.14.
3.10 is not: it reached end of life in October 2026, Polars 2 needs 3.11, and
`dienr.status` uses `enum.StrEnum`. mypy targets 3.12 because NumPy's type
stubs need it; that affects type-checking only.

## Tests, lint and types

```bash
uv run pytest -q                                   # full suite, ~30 s
uv run pytest tests/test_design.py -k masks        # a subset
uv run pytest -q --cov                            # settings in pyproject.toml
uv run ruff check . && uv run ruff format .
uv run mypy                                        # files and settings in pyproject.toml
```

All four must pass before a change is merged. New tests should build their
own inputs (`tests/fixtures/scenarios.py`, `tests/fixtures/bigwig.write_intervals`)
so they always run. Tests that need the R reference's example BigWigs skip
when `_reference/` is absent; the committed parity goldens still run.

What the suite is built to catch, and the habits behind it, is described in
[CLAUDE.md](CLAUDE.md) ("How the suite is structured"). In short: every bug
gets a regression test, fast paths are tested for equivalence with the
reference path, and every `FitStatus` is reached deliberately so a failure can
never turn into a zero.

## R parity

The default configuration reproduces R DENR (commit `09d6cde`) exactly. Golden
values are frozen R output under `tests/fixtures/parity/`; the inputs are
generated by us, never copied from the R package (its licence metadata
conflicts). To regenerate them you need the DENR container:

```bash
uv run python -m tests.fixtures.generate --output build/parity-inputs
singularity exec denr_latest.sif Rscript scripts/export_r_golden.R \
    --inputs build/parity-inputs --output tests/fixtures/parity \
    --commit 09d6cde5ef7ad1a6eb140c6e25dbae91e2a9a819
```

See `tests/fixtures/parity/README.md`. If you clone the R reference for
comparison, put it in `_reference/` (ignored by git) and don't copy or adapt
its source into this repository: `dienr` is implemented from the paper and
from observed behaviour.

## Changing behaviour

`notes/denr-python-implementation-plan.md` is the design spec and the record
of every validation experiment; [notes/README.md](notes/README.md) gives its
conventions. The ones that matter most:

- **Read the relevant plan section before changing behaviour.** It records
  why things are as they are, including decisions not to do something.
- **Never split or renumber the plan.** Its section numbers are cited from
  code, tests, scripts and commits. Add a subsection instead.
- **Write the decision rule before running an experiment**, in the script's
  docstring, and commit it first. Report the result against that rule even
  when it fails.
- **Correct mistakes visibly**: say what was wrong and why, rather than
  editing the old text away.
- **Record random seeds** for every simulation you report.
- **When a recommendation changes**, update `docs/` and add a plan
  subsection.

`docs/` is the user guide and holds current recommendations only; `notes/` is
the history.

## Benchmarks and long experiments

Validation scripts live in `scripts/` (the plan's notes/README maps each to
its section). Run anything long or timing-sensitive on a cluster or dedicated
machine rather than a shared login node, and compare configurations **on the
same node**: node-to-node differences of 4x have been seen at every stage.

## Pull requests

Keep a pull request to one purpose, describe what changed and how it was
checked, and include the plan section it touches, if any. CI
(`.github/workflows/ci.yml`) runs the four checks above on Python 3.11–3.14,
on macOS, and with the `compat` extra, with `uv.lock` enforced (`UV_LOCKED`):
run `uv lock` after changing dependencies. One job uploads coverage to
Codecov, where it is reported but never enforced (`codecov.yml`). CI also
builds both distributions and smoke-tests the wheel in a clean environment.

## Releasing

1. Bump `version` in `pyproject.toml` and `CITATION.cff`.
2. Optionally, run the *Publish* workflow by hand to upload to TestPyPI.
3. Publish a GitHub release tagged `v<version>`. `.github/workflows/publish.yml`
   checks the tag against the package version, builds, and uploads to PyPI by
   trusted publishing; there is no API token.

One-time setup: register this repository as a trusted publisher on pypi.org and
test.pypi.org (workflow `publish.yml`, environments `pypi` and `testpypi`) and
create both environments under Settings → Environments.
